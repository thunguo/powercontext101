Before adding a sixth host, discover what the host can actually provide. Without a stable prompt event, pre-dispatch injection point, or permission API, copying another adapter will not preserve its guarantees.

## Capability discovery

Record prompt event, turn/session identity, workspace, transient injection channel, tool registration, permission/UI, package and Skill installation, headless lifecycle, and version probe.

## Adapter contract

```text
PromptEvent
ScopeResolver
PreparedContextProvider
TransientInjector
SourceCapture
FlushCoordinator
ToolSurface
PermissionGate
Diagnostics
Installer / Doctor
```

Define input, output, failure policy, and observable assertions for each. Automatic helpers may fail open; explicit mutation may not.

## Reuse current implementation

- `powercontext.transport` and loopback vectors;
- Codex/Claude prepared-context schema validation;
- host-specific Scope normalization tests;
- Pi pending flusher;
- DSH OpenAPI-derived operation table;
- Codex/Claude Skill projections;
- setup/doctor catalog in `cli/hosts.py`.

There is no unified HostAdapter SDK today. Do not invent one for cleaner documentation.

## Acceptance tiers

1. Unit contract: schema, Scope, size, secret, permission.
2. Service chain: real Server, Source/Memory lineage, fail-open.
3. Setup/doctor: idempotency, ownership, rollback, activation.
4. Real-host E2E: launch host, send prompt, observe injection/capture/permission.
5. Negative/security: Server down, wrong auth, redirect, unknown schema, oversize, stale turn, no UI, flush timeout.

Managed Skill export currently supports Codex and Claude Code only. Adding export for a new host requires a projection contract and drift tests; a bundled Skill is not enough.

## How to start a sixth host

Do not begin by copying `POST /v1/context/prepare`. Write in this order:

1. Discover host capability first: prompt event, injection channel, permission / UI, and version probe. If one of those is missing, mark **Unsupported** or **Not validated** and do not start an installer.
2. Compare at least two existing hosts. Read [Hooks and plugins](/en/coding-agents/hooks-and-plugins), then compare [OpenCode](/en/coding-agents/opencode) (real host-process E2E is **Supported** and **Version-gated** `>=1.18.21,<2`) with [Codex](/en/coding-agents/codex) (hook plus MCP; real host E2E is **Not validated**).
3. Write tests before the adapter. Name these existing modules:
   - unit contract: `tests/test_transport.py`, `tests/codex_plugin/test_recall.py`, `tests/claude_code_plugin/test_hook.py`
   - service-chain: `tests/e2e/test_codex_service_chain.py`, `tests/e2e/test_dsh_http_chain.py`
   - setup / doctor: `tests/test_setup_select.py`, `tests/test_doctor_integrations.py`, and the matching `tests/test_*_cli.py`
   - real-host E2E: treat `tests/e2e/test_opencode_plugin_host.py` as the current bar; an HTTP-only chain is not enough
   - negative security: Server down, wrong auth, redirect, unknown schema, oversize, stale turn, no UI
4. Add the name to `FIRST_CLASS_HOSTS` in `cli/hosts.py` only after the version gate, idempotent setup, activation probe, and real-host E2E exist. A standalone `setup` command, such as WorkBuddy, does not enter that catalog by itself.

There is no unified HostAdapter SDK. Do not invent one to make the docs look symmetrical.

## Delivery checklist

- Host version gate and activation probe exist.
- Scope comes from stable authorized identity.
- PreparedContext is transient and untrusted.
- Capture states content, size, and secret policy.
- Explicit writes define permission and no-UI behavior.
- Diagnostics leak no content or credentials.
- Setup preserves foreign config and reports rollback or partial failure.
- Real-host E2E exists; an HTTP-only chain is insufficient.
- Unsupported and Not validated remain separate.

Only then add the host to the first-class catalog.
