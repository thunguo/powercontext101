上一页直接写入了已经确认的 Memory。现在走另一条路径：先 capture Source，再让 generation pipeline 从证据中提取长期知识。

两条路径都可能得到 Memory，但它们的前提、lineage 和失败方式不同。

## 两条路径先放在一起看

| 路径 | 需要模型 | 是否先创建 Source | 适合什么 |
|---|---:|---:|---|
| `remember_memory` | 否 | 否 | 你已经知道要保存的事实、决策或约束 |
| capture → flush/scheduler → extraction | 是 | 是 | 从一批工作证据中找出值得长期保留的内容 |

如果 Agent 已经明确得到用户指令“记住这条决策”，直接 remember 更简单。不要为了获得漂亮 lineage，先人工造一条 Source 再绕回 Memory。

反过来，宿主自动捕获的 prompt 通常只应该成为 Source。模型是否把它提炼为 Memory，是后续判断。

## 先检查 extraction capability

```bash
powercontext capabilities
```

必须看到：

```text
Memory extraction: enabled
```

如果是 disabled：

- capture 仍可成功；
- Source 会留在 journal；
- pending Source window 无法执行 model extraction；
- 先运行配置流程，再用 `--env-file` 重启 Server。

```bash
powercontext config init --output .env
powercontext config show --env-file .env
powercontext config validate --env-file .env
powercontext server run --env-file .env
```

是否开启 scheduler 是另一件事。本页主动调用 `flush_memory`，不依赖定时任务。

## 完整 lineage 脚本

新建 `source_memory.py`：

```python
import asyncio
import os
from uuid import uuid4

from powercontext.client import PowerContextClient
from powercontext.http import (
    CaptureContentSourceRequest,
    FlushMemoryRequest,
    ListMemoryEntriesRequest,
    PrepareContextRequest,
    SearchMemoryRequest,
)


SERVER_URL = os.getenv(
    "POWERCONTEXT_CLIENT_SERVER_URL",
    "http://127.0.0.1:8000",
)
API_TOKEN = os.getenv("POWERCONTEXT_CLIENT_API_TOKEN")


async def main() -> None:
    scope_id = f"project:powercontext-101:{uuid4().hex}"
    source_id = "openapi-task-1"

    async with PowerContextClient(
        SERVER_URL,
        token=API_TOKEN,
        timeout=30.0,
    ) as client:
        capabilities = await client.get_capabilities()
        if not capabilities.memory_extraction:
            raise RuntimeError(
                "Memory extraction is disabled. Configure a generation "
                "model and restart the Server with --env-file."
            )

        request = CaptureContentSourceRequest(
            scope_id=scope_id,
            source_id=source_id,
            content=(
                "Decision: after changing the OpenAPI contract, regenerate "
                "and inspect the checked-in client before contract tests."
            ),
            metadata={
                "origin": "powercontext-101",
                "chapter": "source-and-memory",
            },
        )

        captured = await client.capture_content_source(request)
        assert captured.status == "accepted"
        print("source:", captured.source)
        print("position:", captured.position)

        replayed = await client.capture_content_source(request)
        assert replayed.source == captured.source
        assert replayed.position == captured.position
        print("identical replay kept the original position")

        flushed = await client.flush_memory(
            FlushMemoryRequest(scope_id=scope_id)
        )
        print("flush status:", flushed.status)
        print(
            "cursor:",
            flushed.previous_cursor,
            "->",
            flushed.current_cursor,
            "high watermark:",
            flushed.high_watermark,
        )
        print("processed source count:", flushed.processed_source_count)
        print("memory:", flushed.memory)

        if flushed.current_cursor < captured.position:
            raise RuntimeError(
                "The cursor has not reached the captured Source yet. "
                "Flush again or inspect the generation failure."
            )

        page = await client.list_memory_entries(
            ListMemoryEntriesRequest(
                scope_id=scope_id,
                include_inactive=True,
            )
        )

        linked = [
            entry
            for entry in page.entries
            if captured.source in entry.source_refs
        ]

        if not linked:
            print(
                "The Source window was consumed, but extraction produced "
                "no Memory entry linked to this Source. This is a valid "
                "no-op; inspect the model output and content, then retry "
                "with a new Source ID if you need a positive lineage check."
            )

        for entry in linked:
            print("entry:", entry.kind, entry.text)
            print("citation:", entry.citation)
            print("source refs:", entry.source_refs)
            assert captured.source in entry.source_refs

        search = await client.search_memory(
            SearchMemoryRequest(
                scope_id=scope_id,
                query="What should happen before contract tests?",
                mode="auto",
                limit=10,
            )
        )
        print("search mode:", search.mode)
        print("hits:", len(search.hits))

        prepared = await client.prepare_context(
            PrepareContextRequest(
                scope_id=scope_id,
                query="What should happen before contract tests?",
            )
        )
        print("prepared status:", prepared.status)
        print(prepared.content)


if __name__ == "__main__":
    asyncio.run(main())
```

运行：

```bash
uv run python source_memory.py
```

Generation output 本身有不确定性。教程使用明确的 durable decision，提高产生 candidate 的概率，但不能把某段模型文本写成固定预期输出。真正稳定的断言是 position、cursor、exact SourceRef 和 entry lineage。

## 每一步应该看什么

### Capture

成功状态是 HTTP 202，response 包含：

- `status="accepted"`；
- exact content SourceRef；
- scope-local numeric `position`。

同 identity、同序列化 payload bytes 的重放返回原 position。

这个幂等比较不是语义 canonicalization。metadata 键顺序变化可能改变序列化 bytes，从而返回 `source_conflict`。实际重试应复用同一序列化输入。

同 identity 改 content 一定不能覆盖旧 Source，应返回 HTTP 409。

### Flush

判断 Source 是否被消费，看：

- `previous_cursor`；
- `current_cursor`；
- `processed_source_count`；
- capture response 的 `position`。

当前 cursor 达到或超过 capture position，才说明该窗口已被处理。

Scheduler 可能抢先完成工作，所以手动 flush 返回 `idle` 也可能正常。此时 cursor 应已经到位。

### Memory lineage

不要只看 search 是否出现相似文本。查找 `entry.source_refs` 是否包含 capture response 的 exact SourceRef。

这才能证明当前 Memory entry 来自这条 Source。

### Extraction no-op

合法情况：

```text
status = processed
processed_source_count > 0
current_cursor advanced
memory = null, or no linked entry
```

模型可能没有产生 candidate，或者 candidate 与 active content 重复后被去重。Source 已经消费，但 Memory 不一定改变。

## 验证 vector，需要更严格的断言

如果 `capabilities.search_modes` 包含 `vector`，可以额外请求：

```python
vector = await client.search_memory(
    SearchMemoryRequest(
        scope_id=scope_id,
        query="generated client contract tests",
        mode="vector",
        limit=50,
    )
)
```

只有同时满足以下条件，才算验证这条 lineage 的 embedding round trip：

- response `mode == "vector"`；
- hit Citation 指向刚才的 source-linked entry；
- `matched_by` 包含 `vector`。

命中另一条历史 entry、空 hits 或 `mode=None` 都不能证明本次 Source 已建立 vector projection。

显式 `vector` 请求在 capability 不可用时返回 HTTP 422，不会自动切成 FTS。

## 跨会话召回靠 Scope，不靠 session

脚本为了可重复测试使用随机 Scope。要验证跨会话：

1. 改成稳定值，例如 `project:powercontext-101`；
2. 第一次运行 capture/flush；
3. 在新的 Python 进程或 Agent session 中只运行 search/prepare；
4. 两边连接同一个 Server，并使用完全相同的 Scope。

如果第二次查不到，依次检查：

- Server URL；
- database home/URL；
- 最终 `scope_id`；
- entry 是否 active；
- query 是否相关。

Session ID 不应该替代 project Scope。

## Active、inactive 与历史

Extraction 产生的 entry 与显式 Memory 使用同一 lifecycle：

- revise 创建新 entry version；
- retire 将 current entry 设为 inactive；
- 默认 list/search/PreparedContext 只使用 active content；
- `include_inactive=True` 和 exact read 保留审计历史。

Source lineage 也随 entry version 保存。修订时，新的 evidence 会加入 lineage，旧版本的 exact evidence 不会消失。

## 失败排查

### Capture 成功，flush 返回 503

检查 generation capability 和 provider credential。Source 已经保存；修复配置后可以重试未消费窗口。

### Flush 是 processed，却没有 linked entry

这是允许的 no-op。先看 Source 内容是否确实包含可复用决策，再检查 generation 输出和去重。

### Cursor 一直追不上 position

查看 readiness、generation diagnostics 和 scheduler/flush error。不要把未处理窗口误报成已生成 Memory。

### Search 能命中，但 lineage 不对

你命中了同 Scope 中旧的相似 Memory。以 `source_refs` 和 exact entry Citation 为准。

### 第二次 capture 变成 conflict

同一 `source_id` 的 content 或 metadata bytes 发生变化。为新事件使用新 ID；真正的重试则复用原输入。

## 完成检查

这一页完成后，你应能证明：

- capture 创建 Source，不直接创建 Memory；
- replay 保持原 position；
- flush cursor 到达 capture position；
- source-linked entry 通过 exact `source_refs` 被识别；
- processed window 可以合法 no-op；
- 跨进程召回依赖稳定 Scope；
- inactive entry 退出默认召回，但历史仍在。
