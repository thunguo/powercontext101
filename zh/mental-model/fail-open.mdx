PowerContext 是宿主任务旁边的一层上下文能力。Server 暂时不可用时，写代码、回答问题或继续工作不应该一起停下。

这就是 fail-open 的用途。但它只适用于自动、辅助性的路径。用户明确要求保存、批准、commit 或 export 时，失败不能被藏起来。

## PreparedContext 是一次请求的临时值

宿主调用 `prepare_context` 时会提供：

- `scope_id`；
- 当前 query；
- `max_bytes` 字节预算。

Server 从当前 active Memory 和 approved current Experience 中选择相关内容，再返回一个 `PreparedContext`。

正常结果有两种：

| status | 含义 | 宿主行为 |
|---|---|---|
| `ready` | 有非空内容，且 `content_bytes` 与实际 UTF-8 字节数一致 | 将内容作为不可信历史证据临时注入 |
| `empty` | 没有合适内容 | 不注入，继续原任务 |

`empty` 不是 Server 故障，也不是认证失败。

PreparedContext 带精确 Citation，并使用明确的 trust marker：

```text
BEGIN_POWERCONTEXT_PREPARED_CONTEXT_V1
{"trust":"untrusted_history","items":[...]}
END_POWERCONTEXT_PREPARED_CONTEXT_V1
```

宿主不能因为这段内容来自 PowerContext，就把它提升为 system instruction。Citation 说明来源与版本，不保证内容仍然符合当前文件、能力和授权。

## 哪些路径可以 fail-open

### 自动 recall

Server down、超时、schema 不认识或响应过大时，宿主跳过注入，继续原来的模型请求。它应记录有界诊断，但不能输出 query、Scope、准备好的内容、token 或 response body。

### 自动 prompt 或 turn capture

capture 失败不应中止宿主任务。它也不能删除已经准备好的有效 context。

反过来也一样：recall 失败时，支持 capture 的宿主仍可尝试保存 Source。这两条路径不是一个事务。

### 可选 boundary flush

有些宿主会在 capture 后或会话边界尝试 flush，帮助新 Source 尽快进入 extraction pipeline。flush 追不上 cursor 或 Server 暂时不可用时，当前 turn 仍可继续。

### 统计和 telemetry

统计失败不应让已经成功的领域写入回滚。

## 哪些操作必须明确失败

| 操作 | 为什么不能静默继续 |
|---|---|
| `remember` / revise / retire | 调用者明确要求改变长期 Memory |
| Handoff commit | 失败后不存在新的 durable milestone |
| Candidate revise / approve / reject | Review 必须绑定已检查的 Candidate version |
| Skill export / publish | 冲突或本地 drift 时不能覆盖宿主目录 |
| 鉴权与 transport 检查 | fail-open 不能绕过访问控制或把 token 发给其他地址 |

显式操作失败后，宿主的对话本身可以继续，但必须说明这次动作没有完成。

<Warning>
不要写“已保存”再在日志里记录失败。对于显式 mutation，用户看到的结果必须和持久状态一致。
</Warning>

## 一次对照实验

假设 Claude Code 收到：

```text
What should I do after changing the OpenAPI contract?
```

Hook 会分别尝试 recall 和 prompt capture。

### Recall 失败，capture 成功

- 不注入 PreparedContext；
- 原 prompt 继续交给 Claude Code；
- prompt Source 仍可能保存成功；
- 诊断标记 `server_unavailable` 或对应的失败类别。

### Recall 成功，capture 失败

- 已验证的 `additionalContext` 仍然注入；
- capture 错误不会抹掉 recall 结果；
- 当前任务继续。

### 显式 retire 失败

用户随后通过 MCP 要求 retire 一条精确 Memory。此时 Server 已停止：

- MCP operation 返回 unavailable/error；
- 宿主不能声称 Memory 已停用；
- 用户可以继续其他工作，等 Server 恢复后重试。

这三种情况都“不中断宿主”，但只有前两种属于自动 fail-open。

## 安全边界仍然 fail-closed

### 认证失败不是空召回

401/403 表示配置或授权有问题。把它当成 `empty` 会掩盖故障，也可能让用户误以为当前 Scope 没有历史。

### 不跟随 redirect

Hook 不应携带 Authorization header 跟随 30x 到另一个 host。重定向目标拿不到凭证比“尽量完成 recall”更重要。

### 不接受未知 schema

响应能解析成 JSON，不代表宿主理解它。schema version 不匹配时跳过注入，记录 `version_mismatch` 或 `invalid_response`。

### 不接受无限响应

Hook 对响应大小和总墙钟时间设上限。超过限制就中止自动路径，不读取到内存后再处理。

### 不放行不安全 transport

PowerContext Client 拒绝非 loopback 的明文 HTTP。Server 绑定非 loopback 地址时，默认也要求认证或显式 unsafe opt-in。fail-open 不能取消这些检查。

## `degraded` 不等于 `not_ready`

Readiness 把数据库故障和可选 inference 故障分开：

- database/runtime 不可用：`not_ready`，HTTP 503；
- 已配置的 generation 或 embedding probe 失败：`degraded`，HTTP 200；
- 不依赖故障 inference capability 的数据库操作仍可继续；需要该 generation 或 embedding provider 的具体操作仍可能失败。

因此，看到 `degraded` 时先检查具体 capability，不要把整个 Server 当成离线。

## 诊断应告诉你什么

好的自动路径诊断只包含排错所需的元数据，例如：

```json
{
  "component": "powercontext.claude_code.recall",
  "event": "context_prepare",
  "outcome": "server_unavailable",
  "http_status": 503
}
```

它不应包含 prompt、Scope、Memory 文本、Citation、token 或 provider response body。

常见 outcome 包括：

- `empty`
- `authentication_failed`
- `version_mismatch`
- `server_unavailable`
- `invalid_response`

## 判断规则

遇到失败时，问两个问题：

1. 这是宿主自动尝试的辅助操作，还是用户明确要求的持久动作？
2. 跳过它会不会让用户误以为状态已经改变？

自动辅助路径通常可以继续。任何会改变长期状态、批准内容或发布文件的动作，都必须返回真实结果。
