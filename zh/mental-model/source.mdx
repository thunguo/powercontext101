采集成功，但 <Tooltip headline="Memory" tip="经过选择、以后还会用到的项目知识。" cta="阅读 Memory" href="/zh/mental-model/memory">Memory</Tooltip> 搜索仍是空的。这多半不是写入失败。

<Tooltip headline="Source" tip="记录发生过什么。采集不会自动写成长期知识。" cta="阅读 Source" href="/zh/mental-model/source">Source</Tooltip> 记录“发生过什么”。一条用户提示词、一次任务结果，或者宿主捕获的回合，都可以成为 Source。它不负责判断内容是否值得长期保留。那个判断属于 Memory、Experience、Skill 或 Handoff。

应把它们看成两个可观察阶段。Source 已经安全保存，只是抽取窗口还没产出可复用知识。

<Info>
安装参数、接口说明和部署配置，以 [官方文档](https://oceanbase.github.io/powercontext/) 的最新发布版本为准。这页帮你分清证据、日志位置和处理进度。
</Info>

## 先拿到稳定身份

PowerContext 用两个字段引用 Source：

```text
SourceRef
├── source_type
└── source_id
```

完整身份还包括 `scope_id`。同一个 `source_type` 和 `source_id` 可以出现在不同 Scope 中，互不影响。

对于内置内容 Source，一次采集会返回 SourceRef 和 Scope 内部日志位置：

```json
{
  "status": "accepted",
  "source": {
    "source_type": "content",
    "source_id": "openapi-task-1"
  },
  "position": 1
}
```

`source_id` 应稳定且可重现。宿主通常根据 Scope、会话、轮次或内容生成它，以便重试时保持幂等。

## 已采集和引用式不一样

Source 适配器有两种 materialization。

| 类型 | 保存什么 | 读取方式 |
|---|---|---|
| `captured` | PowerContext 保存内容快照和元数据 | 直接从持久层读取 |
| `referenced` | PowerContext 保存外部材料的引用 | 读取时由适配器解析 |

已采集 Source 适合提示词、任务结果和事件文本。引用式 Source 适合由其他系统管理的材料。

差别很实际：已采集内容是当时的快照；引用式材料以后再次解析时，外部内容可能已经变化。

## 一条 Scope 内共用一条日志

Source 被持久化后会得到单调递增的位置。位置：

- 从 1 开始；
- 只在当前 Scope 内有意义；
- 不同 Source 适配器共用同一序列；
- 幂等重试不会占用新位置。

假设先后捕获两条内容：

```text
content/openapi-task-1 → position 1
content/openapi-task-2 → position 2
```

Source 日志解决顺序问题。它不表示哪条 Source 已经被处理，也不表示已经生成 Memory。

## 触发器只选窗口

`SourceWindowTrigger` 是纯策略。它比较 high watermark 和当前游标，然后返回下一段固定窗口：

```text
state.sequence = 0
high_watermark = 2
limit = 1

ProcessSourceWindow(after=0, through=1)
```

下一次激活得到：

```text
ProcessSourceWindow(after=1, through=2)
```

游标已到 2 时，不再返回动作。

窗口写作 `(after, through]`：不含 `after`，包含 `through`。`source_window_limit` 只限制一次处理多少条，不限制日志总长度。

触发器不读取模型，也不执行抽取。它只返回新状态和待执行动作。

## 游标记录消费进度

这里有两个容易混淆的数字：

- 游标 `序号`：业务上处理到哪个 Source 位置；
- 已保存游标 `generation`：保存游标时的并发控制版本。

例如，游标可能表示已经处理到位置 12，同时数据库行的生成是 4。它们没有数值对应关系。

PowerContext 处理 Source 窗口时，会先完成抽取和 Memory apply，再保存新的游标。Memory apply 失败时不能提前推进游标，否则失败窗口会被跳过。

## 采集不会自动产生 Memory

下面的调用只创建 Source：

```http
POST /v1/sources/content
```

要得到 Memory，还有两种路径：

1. 你已经知道要保存什么，直接调用显式 Memory 写入；
2. 配置生成流程，由调度器或 `flush_memory` 处理未消费的 Source 窗口。

即使抽取正常运行，模型也可能认为当前窗口没有值得新增或修订的内容。Source 被处理不保证 Memory Revision 一定变化。

<Note>
`flush_memory` 处理待消费 Source。它不是 `remember_memory` 的另一种写法。
</Note>

## 幂等和冲突

同一 Scope 中，重复采集相同 Source 标识时：

- 持久层序列化后的载荷字节完全相同：返回原来的位置；
- 载荷字节不同：返回冲突，不覆盖旧 Source。

这个比较不是语义规范化。即使元数据表达同一组键值，键顺序导致序列化字节变化时也可能冲突。重试应复用同一序列化输入。

所以不要长期复用固定 `source_id`，却每次写入不同内容。

并发行为同样有明确约束：

- 多条不同 Source 并发写入，位置保持连续，无缺口；
- 同一 Source 的相同载荷并发重试，最终都指向同一个位置；
- 两个工作进程同时更新游标时，只有符合预期生成的写入成功。

## Source 不只来自聊天

Source 不只来自聊天宿主。工作连续性也把事件保存为精确 Source，例如：

- 工作契约（Work Contract）；
- Handoff 边界；
- Handoff 确认回执；
- Task Outcome。

这使 Handoff 报告可以从日志投影工作历史，而不必改写底层 Handoff Artifact。

## 用 OpenAPI 案例推演

捕获第一条证据：

```json
{
  "scope_id": "project:powercontext-101",
  "source_id": "openapi-task-1",
  "content": "The OpenAPI contract changed. Regenerate the checked-in client and run contract tests.",
  "metadata": {
    "origin": "tutorial"
  }
}
```

检查四件事：

1. 响应中的 SourceRef 是否为 `content/openapi-task-1`；
2. 位置是否大于 0；
3. 相同请求重试是否返回同一位置；
4. 修改内容后复用同一 ID 是否返回冲突。

然后再决定：这是只需要保留的证据，还是应该显式写成 Memory。别急着把所有 Source 都变成长期知识。

## 卡住时先对这几条

### 采集成功，但 Memory 没变化

先看生成能力，再看游标是否到达采集位置。两者都正常时，抽取仍可能得到无变更。

### 刷新返回 idle

调度器可能已经先处理了窗口。比较 `current_cursor` 与采集位置，不要只看 `idle` 字样。

### 重试变成冲突

检查是否复用了 `source_id`，但规范形式内容或元数据已变化。

### 不同宿主出现相同位置

只要它们使用同一 Scope 和 Server，这很正常。所有适配器共用 Scope 内部日志。

## 怎么知道分清了

1. Source 标识是否同时包含 Scope、type 和 ID？
2. 日志位置和游标序号是否分开？
3. 游标序号和游标生成是否分开？
4. 窗口是否按 `(after, through]` 理解？
5. 采集是否被误写成 Memory 写入？
6. 幂等重试是否保持原位置？

对不上时，先对[排错](/zh/start/troubleshooting)。要亲手走一遍采集和抽取，看 [Source 与 Memory](/zh/basic-usage/source-and-memory)。
